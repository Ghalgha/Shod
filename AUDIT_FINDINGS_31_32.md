# Дополнительное исследование пунктов 31–32

Ветка: `migration/phase-1-foundation`

Дата проверки: 2026-11-28

Область документа ограничена обработкой IPv4-фрагментации в DirectRelay и распределением пакетов по worker-ам на клиенте и сервере. Другие аспекты транспорта VK Calls не рассматриваются.

## Краткий вывод

Подтверждены три связанные проблемы:

1. Клиентский DirectRelay распознаёт только фрагменты с ненулевым смещением и не отклоняет первый фрагмент, у которого установлен флаг MF.
2. Клиентский dispatcher и серверный TUN dispatcher строят разные FlowKey для первого и последующих IPv4-фрагментов: первый получает TCP/UDP-порты, остальные — нулевые порты. IPv4 Identification в ключ не входит.
3. Даже после исправления FlowKey одинаковый ключ сам по себе не гарантирует, что все части одной дейтаграммы останутся на одном worker: планировщик допускает смену worker на границе 16-КБ burst, а таблица привязок очищается целиком при достижении лимита.

Рекомендуется исправлять все три участка согласованно. Код в рамках этого исследования не изменялся.

## Пункт 31. IPv4-фрагменты в DirectRelay клиента

Файл: `rust-client/src/transport/relay/direct_relay.rs`

### Текущее поведение

В `try_handle()` вычисляется IPv4 fragment offset:

- если offset ненулевой, пакет отклоняется DirectRelay;
- если offset равен нулю, обработка продолжается;
- флаг MF (More Fragments) отдельно не проверяется.

Первый фрагмент IPv4-дейтаграммы имеет offset=0. Если у него установлен MF=1, он всё равно проходит эту проверку как будто это нефрагментированный пакет.

### Последствие

Для TCP первый фрагмент может быть принят DirectRelay и отправлен напрямую, в то время как следующие фрагменты отклоняются DirectRelay и идут через обычный VPN-маршрут. Части одной IP-дейтаграммы оказываются на разных маршрутах, что может нарушить её доставку и сборку на стороне получателя.

Для UDP есть дополнительная проверка длины UDP-дейтаграммы в обработчике: если в первом фрагменте нет всей заявленной UDP-длины, пакет отклоняется. Поэтому описанный риск принятия первого неполного фрагмента не следует автоматически переносить на UDP. Общая ошибка распознавания фрагментации, тем не менее, остаётся.

### Предлагаемое исправление

DirectRelay должен отклонять любой IPv4-фрагмент, если выполняется хотя бы одно условие:

- MF установлен;
- fragment offset не равен нулю.

Проверку следует выполнять до попытки разобрать транспортный заголовок и применить прямую маршрутизацию. Собирать IP-фрагменты внутри DirectRelay для этого исправления не требуется: они должны целиком проходить обычный VPN-маршрут.

## Пункт 32. Согласованное распределение фрагментов по worker-ам

### 1. Клиентский dispatcher

Файл: `rust-client/src/dispatcher/dispatcher.rs`

Функция `flow_key()` разбирает IPv4 source, destination и protocol. Далее:

- при fragment offset=0 извлекает TCP/UDP source и destination ports;
- при ненулевом offset использует порты 0 и 0;
- IPv4 Identification не включает в FlowKey.

Получается, первый фрагмент и последующие фрагменты одной IPv4-дейтаграммы получают разные ключи. Разные нефинальные фрагменты от одного source/destination/protocol также могут ошибочно получить общий ключ, поскольку их Identification не учитывается.

FlowKey используется функцией `select_deficit_waterfall()` для выбора и временной привязки worker-а. Поэтому дефект влияет на распределение исходящих клиентских пакетов по TURN worker-ам.

### 2. Серверный TUN dispatcher

Файл: `rust-server/src/tun/tun_device.rs`

Серверная функция `flow_key()` использует ту же схему:

- первый IPv4-фрагмент получает транспортные порты;
- последующие получают нулевые порты;
- IPv4 Identification отсутствует в ключе.

Серверная таблица потоков также использует FlowKey для закрепления потока за worker-ом. Следовательно, проблема существует и в обратном направлении — при распределении пакетов, прочитанных из серверного TUN.

### 3. Почему одного добавления Identification недостаточно

В обоих dispatcher-ах используется burst-планирование:

- обычная привязка потока рассчитана на burst размером 16 КБ;
- когда остаток burst исчерпан, планировщик может выбрать другой worker;
- для небольших UDP-потоков есть отдельная sticky-привязка, но она не является универсальной гарантией для всех фрагментированных дейтаграмм.

Поэтому одинаковый FlowKey для всех фрагментов устранит расхождение ключей, но не гарантирует, что все фрагменты одной крупной дейтаграммы останутся на одном worker-е.

Есть и ограничение таблицы привязок:

- таблица рассчитана максимум на 1024 записи;
- при достижении лимита после очистки устаревших записей она может очиститься целиком.

Это может сбросить привязки активных потоков. Решение для фрагментированных дейтаграмм не должно полагаться на то, что обычная flowlet-запись обязательно сохранится до прихода всех фрагментов.

### Предлагаемое исправление

Для IPv4-фрагментов FlowKey должен идентифицировать именно IP-дейтаграмму и быть одинаковым для всех её частей. Минимальный набор полей:

- source IPv4 address;
- destination IPv4 address;
- protocol;
- IPv4 Identification.

Фрагментированность нужно определять по MF **или** ненулевому offset. Это важно и для первого фрагмента с offset=0, MF=1.

Для нефрагментированных TCP/UDP-пакетов можно сохранить существующий ключ с портами.

Кроме корректного ключа, для фрагментированных дейтаграмм нужна отдельная гарантия закрепления за одним worker-ом на время обработки всех её фрагментов. Такая привязка не должна переключаться по обычной границе 16-КБ burst и не должна исчезать из-за общей очистки таблицы flowlet-привязок. В реализации необходимо предусмотреть ограничение ресурсов и срок жизни таких временных привязок, чтобы не допустить бесконтрольного роста памяти.

## Рекомендуемые тесты

### DirectRelay

1. Первый IPv4-фрагмент: offset=0, MF=1 — DirectRelay не принимает пакет.
2. Средний/последующий IPv4-фрагмент: offset>0 — DirectRelay не принимает пакет.
3. Нефрагментированный IPv4-пакет: MF=0, offset=0 — существующее поведение не меняется.

### Клиентский и серверный FlowKey

1. Первый и последующие фрагменты одной дейтаграммы получают одинаковый ключ.
2. Две дейтаграммы с одинаковыми source, destination и protocol, но разными Identification, получают разные ключи.
3. Первый фрагмент с MF=1 распознаётся как фрагментированный, несмотря на offset=0.
4. Нефрагментированные TCP/UDP-пакеты по-прежнему разделяются по портам.

### Закрепление worker-а

1. Все фрагменты одной дейтаграммы направляются одному worker-у.
2. Гарантия сохраняется для дейтаграммы, суммарный размер фрагментов которой превышает 16 КБ.
3. При заполнении/очистке обычной flowlet-таблицы привязка незавершённой фрагментированной дейтаграммы не теряется.
4. Разные Identification не смешиваются и могут независимо распределяться по worker-ам.

Тесты должны быть добавлены отдельно для клиентского и серверного планировщиков.
